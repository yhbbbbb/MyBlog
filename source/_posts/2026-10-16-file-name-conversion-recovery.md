> 真正难的不是把文件移动到另一个目录，而是让程序在文件没写完、网络断开或目标重名时，仍然不会把问题变成文件丢失。

## 摘要

这个项目来自一个很具体的工作场景：员工每天需要把生产环节产生的文件放进正确的网络目录。文件要按名称前缀分到针织 K 类或梭织 W 类，部分中文文件名还要转换成拼音。靠人工完成这些动作，步骤重复，边界情况也很多。

我没有先追求一个“功能很多”的软件，而是从最稳定的规则开始，把文件识别、分类、改名、复制、校验、监控和日志逐步组合起来。最终形成了一款 Python Windows 桌面工具，并通过测试和 PyInstaller 打包成 EXE。

目前资料没有记录每天处理量、节省时间或错误率变化，因此本文只讨论已经实现的设计和验证过程，不虚构量化收益。

## 一、从工作痛点开始

员工的操作看起来很简单：看文件名、判断类别、改名、选择目标目录、复制文件。但这些动作会被大量重复文件放大，而且每一步都可能遇到异常。

| 工作中的情况 | 程序对应的设计 |
| --- | --- |
| 文件数量多，需要逐个判断归属 | 根据文件名前缀自动分流到 K/W 目录 |
| 中文名称不适合后续系统 | 自动转换拼音，并清理 Windows 不允许的字符 |
| 临时文件和正式文件混在一起 | 只处理约定扩展名，跳过临时文件和不符合规则的文件 |
| 目标目录已经有同名文件 | 提供覆盖或自动追加序号两种模式 |
| 文件仍在生成或被其他程序占用 | 处理前等待文件稳定，并检查占用状态 |
| 网络共享目录暂时不可用 | 保留源文件、记录原因，并在网络恢复后重试 |
| 复制中断可能留下半个文件 | 先复制到临时文件，校验后再替换目标文件 |
| 员工不知道程序是否卡住 | 界面显示状态和统计，日志记录每个结果 |

这些需求共同指向一个原则：**正常流程要自动化，失败流程要可恢复**。如果程序只在网络正常、文件完整且没有重名时工作，它就还不能真正承担生产环境里的重复操作。

## 二、先把人工经验变成规则

程序首先需要回答两个问题：哪些文件应该处理，以及它们应该去哪里。

项目把约定的文件名前缀写成分类规则。符合 K 类前缀的文件进入针织目录，符合 W 类前缀的文件进入梭织目录；无法匹配的文件不猜测归属，而是写入日志并跳过。

这种“匹配失败就停在原地”的策略看似保守，实际上更适合文件处理工具。错误地把文件送到另一个生产目录，通常比暂时不处理更难排查。

文件过滤也采用白名单思路：只处理约定扩展名，忽略临时文件和不符合命名规则的文件。规则与业务约定分开后，后续调整前缀或扩展名时，不需要重写复制和监控逻辑。

## 三、一次处理的完整流程

单次批处理和目录监控最终都进入同一条处理链路。这样可以避免“手动扫描一套规则、监控事件又是另一套规则”。

### 1. 过滤和分类

程序先扫描源目录，只把符合约定的文件交给处理器。无法识别的文件会保留在原目录，并在日志中说明原因。这样既避免误处理，也给后续补充规则留下依据。

### 2. 转换文件名

中文文件名通过 `pypinyin` 转换成拼音，同时清理 Windows 不允许的字符。遇到目标目录已有同名文件时，用户可以选择覆盖，或者让程序自动生成带序号的新名称。

### 3. 确认文件可以安全处理

刚生成的文件可能还在写入，网络共享中的文件也可能被其他程序占用。程序会等待文件大小稳定，再检查文件是否可访问。这个等待不是为了拖慢流程，而是避免把半个文件搬走。

### 4. 复制、校验、提交

文件不会直接复制到最终路径。程序先生成临时副本，再核对文件大小和 SHA-256 摘要。校验通过后才替换目标文件，并清理源文件；任何一步失败，都保留源文件并写入失败日志。

## 四、网络文件场景必须有失败保护

本地目录里的复制失败，通常可以重新执行；网络共享目录里的复制失败，还可能伴随连接中断、目标不可达和多台电脑同时操作。

因此，项目把“文件是否可以删除”放在流程最后。只有目标文件已经完整写入并通过校验，源文件才允许被清理。网络暂时不可用时，程序保留源文件，记录失败原因，并由后台任务在网络恢复后重新尝试。

| 风险 | 保护措施 | 结果 |
| --- | --- | --- |
| 文件仍在写入 | 等待稳定、检查占用 | 避免移动半成品 |
| 网络目录不可达 | 设置超时、保留源文件 | 不因网络波动丢文件 |
| 复制中途断开 | 临时文件复制 | 不把半个文件当成正式文件 |
| 目标文件重名 | 覆盖/追加序号模式 | 由用户明确选择结果 |
| 处理失败后无人知晓 | 日志、状态和统计 | 可以回看并继续处理 |

这个设计的核心不是“保证永远成功”，而是让失败变得可见、可解释、可重试。

## 五、从单文件实现拆成模块

功能增加后，所有代码放在一个文件里会让规则、界面和文件操作互相牵连。项目后来按职责拆分到 `rename-to-pinyin/src/rename_to_pinyin/`：

| 模块 | 负责内容 |
| --- | --- |
| `filename_rules.py` | 拼音转换和 K/W 分类规则 |
| `filesystem.py` | 路径校验、安全复制、校验与清理 |
| `processor.py` | 批量处理和状态记录 |
| `monitor.py` | `watchdog` 目录监控与待处理队列 |
| `config.py`、`runtime.py`、`logging_config.py` | 配置、运行目录和日志 |
| `gui.py` | Tkinter 界面和用户操作 |
| `run.py`、`__main__.py` | 启动入口 |
| `tests/` | 规则、文件系统、流程、配置和日志测试 |

拆分的目的不是为了增加目录层级，而是让每个问题有明确的位置。例如，分类错误应该看规则模块，复制校验失败应该看文件系统模块，界面卡住则应该看后台任务和队列。

程序使用 Python 3.12 和 Tkinter 构建 Windows 桌面界面，目录监控使用 `watchdog`，文件锁和系统信息使用 `filelock`、`psutil` 及 Windows 平台依赖，最终通过 PyInstaller 打包为 EXE。

## 六、界面反馈也属于功能

文件处理不是点击按钮后马上结束的操作。网络目录、文件数量和等待时间都会让任务持续一段时间。如果界面没有反馈，员工很难判断程序是在工作、等待还是已经失败。

因此界面提供了这些信息：

- 源目录、K 目录和 W 目录的配置；
- 路径可达性检查；
- 文件处理延迟和覆盖模式；
- 当前运行状态、扫描数、成功数、失败数和跳过数；
- 取消任务和异常提示；
- 监控模式的启动初扫。

监控模式尤其需要启动初扫。否则程序只监听启动之后的新文件，重启期间已经存在的文件可能永远不会进入处理队列。初扫和实时事件使用同一套过滤规则，并通过集合去重，避免同一个文件被重复提交。

## 七、人与 AI 的协作方式

这个项目不是由 AI 一次生成后直接交付，而是围绕真实反馈逐步迭代。作者提供业务约束，例如 K/W 分类规则、网络目录行为、文件生成延迟和员工使用反馈；AI 协助把这些约束拆成模块、代码和测试。

协作通常从一个具体现象开始：

1. 先描述员工遇到的实际问题，例如网络中断时不能删除源文件。
2. 再明确程序必须遵守的边界，例如校验通过前不得清理源文件。
3. 确定实现位置和验证方式。
4. 运行测试、编译、打包或启动检查。
5. 根据结果继续修正，而不是把未验证的建议当成结论。

这里的 AI 更像工程协作助手。它可以帮助整理规则、拆分模块和补充测试，但业务判断、生产约束和最终验收仍需要由使用者确认。

## 八、测试、打包与发布

项目为规则、文件系统、处理流程、配置和日志建立了独立测试。随着网络重试、日志留存、配置保存和启动扫描等行为加入，测试数量在不同阶段逐步增加。历史记录里的数量对应不同代码阶段，不能直接当作当前固定测试总数；发布前应重新运行当前测试套件。

除单元测试外，发布前还需要检查：

- Python 源码是否可以编译；
- 依赖是否完整安装；
- PyInstaller 是否成功生成 EXE；
- EXE 文件哈希是否与发布记录一致；
- 打包后的程序能否短时间启动并显示界面；
- 网络失败时源文件是否仍然保留。

## 九、目前还需要补充的数据

当前材料可以说明工具解决了哪些流程问题，但还不能支持具体效率结论。后续如果要评估上线效果，建议补充以下数据：

| 需要补充的内容 | 用途 |
| --- | --- |
| 原来的人工操作步骤和点击次数 | 描述流程改变前后的差异 |
| 实际部署部门、使用人数和处理量 | 说明使用范围 |
| 使用前后的耗时、漏分和重复处理记录 | 形成可验证的效果对比 |
| 正式 EXE 名称、版本和发布日期 | 建立发布记录 |
| 是否有多台电脑同时处理同一目录 | 评估并发和部署约束 |

在这些数据补齐前，比较稳妥的说法是：工具减少了重复判断和手工复制，并为失败情况提供了保留、记录和重试机制。不要直接写成“效率提升 N 倍”或“错误率下降某个百分比”。

## 结语：先解决一个重复痛点，再把边界补齐

一个文件分拣工具的价值，不只在于它能自动移动文件，更在于它能把人工经验变成明确规则，把异常情况变成可观察状态，把失败结果变成可以恢复的任务。

如果你也准备制作类似的内部效率工具，可以从三个问题开始：**哪些判断每天重复发生？哪些失败会造成不可逆损失？哪些结果必须留下证据？** 先回答这三个问题，再决定是否需要界面、监控、重试和打包。

对这个项目来说，下一步不是继续堆功能，而是补齐真实使用数据、确认当前生产规则，并用实际日志验证工具是否真的减少了等待和重复操作。
