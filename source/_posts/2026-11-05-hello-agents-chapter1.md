> 这篇文章是我学习 Datawhale《Hello-Agents》第一章“初识智能体”后的整理。重点不是复述章节，而是把“模型为什么会变成智能体”这件事，用自己的语言和代码经验重新串起来。

## 一、我先理解了：Agent 到底是什么

在没有统一定义时，Agent 很容易被描述成一个“更聪明的聊天机器人”。但这个说法不够准确。聊天机器人通常是收到问题后生成一段文本；Agent 则要围绕一个目标，理解当前状态，决定下一步动作，必要时调用工具，再根据结果继续执行。

我现在比较认同的工程化定义是：

> **Agent 是以大语言模型为决策核心，结合状态、工具、记忆和执行循环，能够在一定边界内完成目标的系统。**

这里有几个关键词：

- **目标**：系统要完成什么，而不只是回答一句话；
- **状态**：当前已经知道什么、做到了哪一步、还缺什么；
- **决策**：下一步是直接回答、继续搜索、调用 API，还是向用户澄清；
- **行动**：把决定落实为工具调用或外部操作；
- **反馈**：读取行动结果，再决定是否继续；
- **边界**：权限、工具白名单、最大步数、超时和人工审批。

因此，Agent 的“智能”并不只来自模型参数，也来自模型周围的系统设计。

## 二、语言模型和智能体有什么区别

大语言模型本身更像一个概率生成器：输入上下文，输出下一个更可能出现的 token。它擅长理解语言、总结、改写、推理和生成代码，但它通常不知道实时库存，也不能凭空访问公司的数据库。

Agent 在模型外面增加了一个执行系统：

{% asset_img agent-vs-llm.svg 大语言模型与智能体系统的差异 %}

| 对比项 | 语言模型 | Agent 系统 |
| --- | --- | --- |
| 输入 | 用户提示和上下文 | 用户目标、历史状态、工具结果 |
| 输出 | 文本或结构化结果 | 文本、工具调用和状态更新 |
| 信息来源 | 训练参数和当前上下文 | 模型、知识库、API、数据库、文件 |
| 执行方式 | 通常一次调用 | 可以多轮决策和行动 |
| 失败处理 | 需要外部程序处理 | 可以重试、改写、换工具或升级人工 |
| 风险边界 | 主要是输出内容风险 | 还包括工具权限和外部副作用 |

这不代表 Agent 一定比普通 LLM 更好。简单的摘要、翻译和文本改写，直接调用模型更便宜、更可控。只有当任务需要多步执行、外部信息或工具协作时，引入 Agent 才有意义。

## 三、智能体的基本闭环：感知、思考、行动

第一章最重要的模型，在我看来是“感知—思考—行动—反馈”的循环：

{% asset_img agent-loop.svg 智能体感知思考行动反馈闭环 %}

### 1. 感知：把外部世界变成状态

感知不一定是摄像头或语音，也可以是读取用户消息、数据库记录、文件内容、网页和工具返回值。系统需要把这些输入整理成模型能理解的上下文。

```python
state = {
    "goal": "查询本月销售额并生成摘要",
    "messages": ["请分析本月销售额"],
    "observations": [],
    "available_tools": ["query_sales", "write_report"],
}
```

状态设计很重要。上下文太少，模型无法判断；上下文太多，又会增加成本和噪声。真正的工程问题不是“把所有内容都塞给模型”，而是保存对下一步有用的信息。

### 2. 思考：决定下一步做什么

“思考”不一定等于暴露一大段思维过程。工程上更重要的是得到可检查的决策结果，例如：

```json
{
  "action": "query_sales",
  "arguments": {"month": "2026-11"},
  "reason": "当前缺少本月销售数据"
}
```

结构化动作比让模型输出一段“我打算……”更容易校验。系统可以检查 `action` 是否在白名单中，参数类型是否正确，用户是否拥有权限。

### 3. 行动：通过工具改变或读取外部世界

工具是 Agent 与现实系统之间的接口。常见工具包括搜索、数据库查询、文件读写、计算器、代码执行和业务 API。

```python
def run_tool(action: dict, tools: dict):
    name = action["action"]
    if name not in tools:
        raise ValueError(f"禁止调用工具：{name}")
    return tools[name](**action.get("arguments", {}))
```

这个例子虽然简单，却体现了一个重要边界：**模型可以提出动作，但执行器决定动作能否真正发生。** 对删除数据、付款、发邮件等操作，执行器还应加入权限检查、参数校验、幂等键和人工确认。

### 4. 反馈：根据结果决定结束还是继续

工具返回成功、空结果、错误或部分结果后，Agent 需要重新判断。一个可靠的循环必须有停止条件：任务完成、达到最大步数、超时、连续失败或需要人工介入。

```python
MAX_STEPS = 5

for step in range(MAX_STEPS):
    decision = decide(state)
    if decision["action"] == "final":
        break
    observation = run_tool(decision, tools)
    state["observations"].append(observation)
else:
    raise TimeoutError("Agent 超过最大执行步数")
```

没有步数和成本边界的 Agent，可能在错误工具、错误查询或互相矛盾的结果之间循环。

## 四、工具调用不是“模型直接执行代码”

我之前容易把工具调用理解为“模型生成 Python，然后程序运行它”。更准确的过程是：模型生成符合约定的工具调用请求，应用程序解析请求，验证参数和权限，再由应用程序调用真实函数，最后把结果反馈给模型。

{% asset_img tool-calling-flow.svg Agent 工具调用的安全执行流程 %}

一个工具描述至少应包含名称、用途、参数类型和限制：

```python
TOOLS = {
    "query_sales": {
        "description": "查询指定月份的销售汇总",
        "arguments": {"month": "YYYY-MM"},
        "permission": "sales:read",
        "read_only": True,
    }
}
```

工具设计要尽量窄。一个叫 `run_any_sql` 的工具权限太大，不如提供参数固定的 `query_sales_summary`；一个允许任意文件路径的工具，也比限定工作目录的工具危险得多。

## 五、记忆、上下文和知识库不是一回事

学习这一章时，我把几个概念区分开后清楚了很多：

### 上下文

上下文是本次模型调用能看到的内容，例如当前问题、最近消息、工具结果和系统提示词。它通常是短期的，受 Token 窗口和成本限制。

### 记忆

记忆是跨轮次或跨任务保存的信息。例如用户偏好、上次任务状态和长期配置。记忆需要考虑更新、过期、删除、隐私和错误信息纠正，不能简单地把所有聊天记录永久拼接。

### 知识库

知识库保存外部资料，如产品手册、制度文件和项目文档。RAG 负责从知识库中检索相关证据；记忆则更关注用户或任务的持续状态。二者可以协作，但不能互相替代。

## 六、Agent 的常见组成方式

按照任务复杂度，可以把系统分成几个层次：

1. **单轮模型调用**：输入提示词，得到回答；
2. **模型 + 结构化输出**：模型生成 JSON，由程序校验和执行；
3. **模型 + 工具调用**：模型根据结果决定是否继续；
4. **模型 + RAG**：先检索外部资料，再生成有依据的回答；
5. **工作流 Agent**：把固定步骤写成图或状态机，模型只负责局部决策；
6. **多 Agent 协作**：不同角色负责规划、检索、执行和复核。

层次越高，能力可能越强，但成本、延迟、调试难度和不可预测性也越高。我的学习原则是：先用最简单的方案验证业务价值，再只为明确的问题增加记忆、工具、RAG 或多 Agent。

## 七、我对“自主性”的理解

Agent 常被宣传为“自主完成任务”，但自主性不应该等于无限权限。真正可用的自主性应该是：

- 在明确目标和工具范围内自主选择路径；
- 在低风险操作上自动执行；
- 在高风险操作前请求确认；
- 在失败和不确定时主动停止并说明原因；
- 每一步都能留下日志，必要时可以回放和恢复。

也就是说，Agent 的边界越清晰，越容易进入真实业务。一个什么都能做、但无法解释和回滚的系统，往往比能力有限但可靠的系统更难使用。

## 八、我的学习收获：先学会设计边界

学习了第一章，让我对 agent 有了更深的感受，也有了以下三个更具体的结论：

### 第一，模型不是完整应用

模型负责语言理解和决策建议，应用程序负责状态、权限、工具执行、错误处理和数据保存。把所有责任都交给模型，会让系统难以测试。

### 第二，工作流和 Agent 可以组合

固定的步骤应该用确定性代码表达；需要理解自然语言和选择路径的地方，再交给模型。这样既保留灵活性，也不会让整个系统变成黑盒。

### 第三，评估要看任务结果

不能因为模型回答听起来流畅，就认为 Agent 成功。还要检查工具参数是否正确、数据是否越权、任务是否完成、成本是否可接受、失败是否可恢复。

## 九、一个适合继续实践的小项目

我准备把本章概念落到一个“项目资料助手”上：

```text
用户提出问题
    -> 判断是否需要检索
    -> 查询项目文档或数据库
    -> 校验来源和权限
    -> 生成回答并附引用
    -> 用户确认后再执行写操作
```

第一版不做多 Agent，也不允许任意代码执行，只提供两个只读工具：文档搜索和项目状态查询。等日志、评估集和失败案例稳定后，再考虑加入写入工具和自动化操作。这种从小范围、低风险、可观察的任务开始，比较符合我对 Agent 学习路径的理解。

## 总结

智能体不是单独一个模型，而是一个围绕目标运行的系统。它以大语言模型为决策核心，通过状态保存上下文，通过工具连接外部世界，通过记忆延续任务，通过循环根据反馈继续或停止。

学习 Agent 时，最值得先掌握的不是“如何让模型更自主”，而是如何设计清晰的状态、工具和边界。只有当输入、动作、结果、异常和停止条件都能被观察和验证，Agent 才从演示效果变成真正可维护的软件。
