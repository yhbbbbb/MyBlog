> **低代码平台降低的是实现门槛，不是思考门槛。真正需要设计的是数据、提示词、工具、权限和失败处理。**

## 开篇：为什么要用低代码平台

第四章用 Python 从零实现了 ReAct、Plan-and-Solve 和 Reflection。这样做有助于理解 Agent 的循环，但真实项目还要处理模型接入、状态管理、知识库、工作流、发布渠道、日志和权限。每个项目都重复实现这些基础设施，验证业务想法的速度会很慢。

低代码平台把常见能力封装成节点、配置项和可视化工作流，使开发者可以把精力放到业务流程和提示词设计上。它不是“不会写代码也能自动得到好产品”，而是把代码工作从底层实现提升到了流程编排和系统边界设计。

## 一、四个平台的定位

| 平台 | 核心定位 | 更适合的任务 | 主要优点 | 主要局限 |
| --- | --- | --- | --- | --- |
| Coze（扣子） | 面向创作者的零代码/低代码 Agent 平台 | 快速做聊天机器人、内容助手和多渠道应用 | 上手快、插件多、发布渠道丰富 | 平台依赖明显，复杂逻辑和私有化能力受限 |
| Dify | 开源的 LLM 应用开发与运营平台 | 企业级 Agent、Workflow、RAG 和 API 服务 | 模型管理、工作流、日志和部署能力完整 | 自部署需要运维，复杂流程仍需代码扩展 |
| FastGPT | 知识库问答与可视化 Flow 平台 | 企业知识库、客服、内部问答 | RAG 链路完整，文档处理和问答体验好 | 通用自动化生态不如 n8n，复杂业务需外接系统 |
| n8n | 通用工作流自动化平台，附带 AI 节点 | 邮件、数据库、SaaS、API 串联 | 连接器多、可自托管、自动化能力强 | Agent 专用能力较少，学习和运维成本较高 |

选型时不要只比较“谁的模型更强”。应先确定数据是否敏感、是否需要自部署、是否依赖企业系统、是否需要多渠道发布，以及团队能承受多少运维成本。

## 二、Coze：快速构建并发布 Agent

### 1. 构建思路

Coze 的基本组成可以理解为：Agent 负责角色和对话，插件负责外部能力，知识库负责私有资料，工作流负责稳定的多步骤处理。以“每日 AI 简报”为例，可以将新闻搜索、内容筛选、分类总结和格式化输出拆成节点，再通过定时触发或手动触发运行。

### 2. 提示词与输出约束

```text
# 角色
你是技术研究助理，负责整理过去 24 小时的 AI 动态。

# 任务
搜索可信来源，筛选新闻、论文和开源项目，去除重复内容。

# 输出格式
## AI 技术新闻
- 标题：
- 来源与链接：
- 核心变化：
- 对开发者的影响：

## AI 学术论文
...

# 边界
找不到可靠来源时明确说明，不要编造标题、数据和链接。
```

Coze 的优势是从想法到可用原型很快，并且能直接接入插件、知识库和发布渠道。局限是平台规则、插件可用性和数据流转方式需要依赖平台；涉及敏感资料或强合规要求时，要先确认存储、权限和审计能力。

## 三、Dify：从原型走向可运营应用

Dify 更像一个 LLM 应用开发平台，而不是单纯的聊天机器人编辑器。它通常把应用分为 Chatbot、Workflow、Agent、知识库和 API 等部分，并提供模型配置、变量、日志、追踪和发布能力。

### 1. 个人助手的配置边界

一个可靠的个人助手至少要分清以下内容：

- **Profile**：身份、目标用户和语气。
- **Skills**：可以执行的能力，例如总结、检索、生成代码。
- **Rules**：安全边界、引用规则和拒答条件。
- **Workflows**：需要固定顺序执行的任务。
- **Initialization**：首次对话时的欢迎语和必要信息收集。

```text
你是我的技术学习助手。
当问题涉及我的资料时，先检索知识库，再回答并标注依据。
当问题需要实时信息时，调用搜索工具并说明检索时间。
当无法确认时，直接说明不确定，不要用猜测补全事实。
涉及删除数据、发送消息或修改线上系统时，必须先请求确认。
```

Dify 的强项是把模型、知识库、工作流和 API 放进同一个可运营环境，适合团队协作和持续迭代。它的代价是部署、模型供应商、向量数据库、对象存储和权限配置都会成为运维责任；“开源”不等于零成本。

## 四、FastGPT：围绕知识库问答优化

FastGPT 的核心链路是“导入资料→清洗分块→向量化→检索→重排→生成回答”。它适合把企业文档、SOP、产品手册和项目资料变成可查询的知识库。

### 1. 智能投顾助手的安全边界

“智能投顾”可以作为信息整理和风险提示助手，但不能把模型输出直接当成投资建议。工作流应要求它引用数据时间、说明信息来源、区分事实与推测，并在无法验证时拒绝给出确定性结论。

{% note warning %}
金融、医疗、法律等高风险场景，知识库问答只能辅助检索和解释；最终决策仍需要人工审核、权限控制和合规流程。
{% endnote %}

FastGPT 的优势是知识库体验和 RAG 链路完整，适合快速验证“文档能不能被准确问到”。局限是它的核心价值集中在知识问答，遇到复杂的邮件、数据库和 SaaS 自动化时，通常需要通过 API 或工作流平台补足。

## 五、n8n：把 Agent 接入真实业务流程

n8n 的核心不是“生成一段回答”，而是把触发器、业务节点、API、数据库和 AI 节点串成可执行流程。例如智能邮件助手可以按下面的路径运行：

## 六、四个平台的综合比较

| 评估维度 | Coze | Dify | FastGPT | n8n |
| --- | --- | --- | --- | --- |
| 上手速度 | ✅ 很快 | ✅ 较快 | ✅ 较快 | ⚠️ 需要理解工作流 |
| RAG 能力 | ✅ 有 | ✅ 完整 | ✅ 强项 | ⚠️ 需自行组合 |
| 通用自动化 | ⚠️ 有限 | ✅ 工作流 | ⚠️ 以问答为主 | ✅ 最强 |
| 私有化部署 | ⚠️ 依平台版本 | ✅ 支持 | ✅ 支持 | ✅ 支持 |
| 多渠道发布 | ✅ 强 | ⚠️ 依 API/前端 | ⚠️ 依集成 | ⚠️ 需自行接入 |
| 企业运维 | ⚠️ 平台依赖 | ✅ 能力完整 | ✅ 适合知识库 | ⚠️ 责任较重 |

我的选型顺序是：先按数据和合规要求筛选部署方式，再按核心任务选择平台，最后才比较界面和模型。快速做公开内容助手可以先选 Coze；要做可运营的 LLM 应用优先评估 Dify；文档问答优先试 FastGPT；需要连接邮件、数据库和业务 API 则优先考虑 n8n。

## 七、章节习题：回答与思考

### 1. Coze、Dify、n8n 与三种开发模式

三个平台解决的不是同一个问题：Coze 追求“快速做出来并方便分享”，Dify 追求“快速且可控地构建 LLM 应用”，n8n 追求“把多个系统连接起来自动运行”。因此不能只按功能数量给平台排名。

| 平台 | 核心定位 | 主要解决的痛点 | 典型场景 |
| --- | --- | --- | --- |
| Coze | 面向创作者的 Bot 和 AI 应用平台 | 降低上手门槛，快速验证交互和分发 | 活动 Bot、内容助手、公开服务 |
| Dify | LLM/Agent 应用开发与运营平台 | 统一管理模型、工作流、知识库、插件和 API | 企业助手、RAG、私有部署应用 |
| n8n | 通用工作流自动化平台 | 连接 SaaS、数据库、API 和消息系统 | 邮件、工单、CRM、数据同步 |

三种开发模式的取舍如下：

1. **低代码优先**：适合需求不确定、需要快速试错、团队工程资源有限的项目，例如每日简报或营销小程序。
2. **纯代码优先**：适合高性能、高定制、高合规场景，例如金融审批、复杂多 Agent 调度和需要深度控制的核心系统。
3. **混合开发**：平台负责对话、路由和可视化编排，代码服务负责企业专有 API、复杂算法和安全控制。例如 Dify 调度工作流，内部 Python 服务访问公司数据库。

我的判断是，企业项目最终多数会走向混合模式：平台提高迭代速度，代码服务守住控制力和集成深度。

### 2. 如何把 Coze 每日简报改成定时推送

核心是把“用户主动询问”改造成“定时触发工作流”：

1. 使用 Coze 的定时任务，或用 n8n、`cron`、云函数每天 8 点调用 Agent/API。
2. 固定执行“抓取资讯→去重筛选→生成简报→发送消息”的链路。
3. 对接飞书群机器人、企业微信机器人或微信公众号发布接口。
4. 保存本次抓取时间、来源链接和发送结果，失败时重试但避免重复推送。

简报 Prompt 不应只要求“写得更长”，而应像一个编辑部流程：固定快讯、重点解读、趋势判断和值得关注对象等栏目；明确事实与观点分离；要求每条内容附来源和“为什么值得关注”；无法确认时标注不确定，不做无依据的预测。受众是工程师、管理者还是普通用户，也应决定摘要粒度。

**MCP（Model Context Protocol）** 可以理解为面向模型的标准化工具和资源接口层。RESTful API 是通用系统通信方式，Tool Calling 是模型调用工具的机制，而 MCP 尝试统一描述工具、资源和提示模板，让不同客户端、模型和工具提供者可以按共同契约连接。若 Coze 支持 MCP，企业内部 API、数据库查询和团队共享工具就能更低成本接入，Agent 的工具生态也不再完全受限于平台插件商店。

### 3. Dify 的分类路由、数据库 Schema 与部署方式

问题分类器的价值是**先缩小问题空间，再让合适的子 Agent 处理**。例如把请求分成知识问答、SQL 查询、文案优化和日程管理，每个子 Agent 只拥有相关 Prompt、工具和知识库。这样可以缩短上下文、减少角色混乱，并让每条链路更容易测试和监控。

如果让一个万能 Agent 处理所有任务，常见问题是：Prompt 过长、工具选择空间过大、不同任务的输出规范互相冲突、权限难以收敛，最终表现为准确率和可维护性下降。分类器本身也要设置“无法判断”和多标签分支，不能强行把所有问题塞进一个类别。

当数据库有 50 张表、每张表 20 个字段时，不应把全部 DDL 放入 Prompt。更好的方案是：

1. 为表名、字段、注释、业务主题和关联关系建立结构化元数据索引。
2. 先根据用户问题检索最相关的 2~5 张表。
3. 只将候选表的 DDL、字段说明和少量示例 SQL 注入上下文。
4. SQL 生成后做语法、权限和只读校验；需要时再二次检索外键关系。

本地部署与云端部署的取舍：

| 维度 | 本地部署 | 云端部署 |
| --- | --- | --- |
| 数据安全 | ✅ 数据边界和网络策略更可控 | ⚠️ 依赖服务商隔离与合规能力 |
| 初始成本 | ❌ 服务器、部署和运维成本高 | ✅ 启动成本低，上线快 |
| 性能控制 | ✅ 可定制模型、缓存和资源 | ⚠️ 受云资源、配额和网络影响 |
| 维护难度 | ❌ 需要自己升级、备份和监控 | ✅ 平台承担大部分基础维护 |
| 适用场景 | 敏感数据、强合规、内网系统 | 验证期产品、小团队、公开数据 |

### 4. n8n 邮件助手的持久化、附件和电商流程

`Simple Vector Store` 与 `Simple Memory` 基于内存，服务重启会丢失数据。持久化改造可以选择 Pinecone、Qdrant、Weaviate 等向量库保存 Embedding 和文档，选择 Redis、PostgreSQL 或其他持久化 KV 保存会话记忆。基本步骤是创建服务、在 n8n 凭据中配置地址和密钥、替换内存节点，并通过重启后的检索测试验证数据仍然存在。生产环境还要设计索引版本、过期策略和备份。

处理 PDF 或图片附件时，工作流应增加：检测附件类型→下载文件→PDF 文本解析或图片 OCR/视觉模型→把结果转换为统一文本/结构化字段→与邮件正文合并→生成回复。必须限制附件大小、验证文件类型，并避免把不可信附件内容直接当作系统指令。

### 5. 平台差异如何影响 Prompt，输出长度是否应硬限制

Coze 更偏前台交互，Prompt 通常强调角色、语气、用户体验和最终展示；Dify 更偏应用与工作流编排，Prompt 更强调任务边界、路由、变量和知识注入；n8n 的 Prompt 常服务于某一个自动化节点，重点是输入输出格式和下游节点可消费性。这些差异与平台形态直接相关：越靠近产品前台，越关注表达；越靠近流程中台，越关注契约。

“输出超过 500 字”只有在公众号草稿、周报等确实需要最低信息量的场景才合理。对于问答、分类和 SQL 生成，硬性长度会导致灌水、上下文浪费和信息密度下降。更稳妥的方式是约束栏目、覆盖点、格式和最大长度；需要完整分析时让模型根据问题复杂度自由展开。

### 6. 没有现成工具时如何接入，MCP 与自定义插件

当三个平台都没有公司内部工具时，可以：

1. 先封装稳定的内部 HTTP API，并补充鉴权、限流、审计和错误码。
2. 平台支持时开发自定义插件或节点。
3. 将复杂能力放在外部 Python/Java 服务，由平台通过 API 调用。

RESTful API 是系统间通用通信接口；Tool Calling 是模型输出工具名和参数的调用机制；MCP 则提供面向 Agent 的标准化工具、资源和提示描述层。MCP 的价值在于减少每个平台重复编写适配器的成本，但它不是安全边界，仍需要权限、参数校验和人工确认。

Dify 自定义插件的基本流程是：明确能力边界和输入输出 Schema；实现插件后端逻辑；定义鉴权、超时、重试和错误处理；在 Dify 中注册、测试和发布；为工具写清晰描述，使路由器能正确选择。内部知识库插件还要处理租户隔离、查询权限、引用来源和敏感字段脱敏。

### 7. 三个应用的最终选型

| 应用 | 推荐方案 | 理由 |
| --- | --- | --- |
| A：C 端 AI 写作小程序 | Coze 或类似快速平台 | 人少、预算有限，首要目标是快速验证需求；后续用户规模和成本达到阈值再迁移 |
| B：企业智能合同审核 | Dify 私有部署 + 外部代码服务，必要时纯代码 | 法律文档敏感，需要私有化、知识库、审计和 OA/文档系统集成；高风险决策必须保留人工审核 |
| C：研发效能工具 | n8n + 纯代码服务，或代码主导自建 | 本质是连接 Git、CI、测试、缺陷和项目管理系统；团队技术能力足够，长期需要版本化、测试和深度定制 |

选择依据不是平台是否“最强”，而是技术可行性、上线速度、成本、可维护性、扩展空间和数据合规的综合结果。我的复习结论是：快速验证选 Coze，企业可控应用选 Dify 私有化，重系统连接选 n8n 或代码主导；关键领域则使用混合架构。

## 八、第五章小结

第五章的重点不是记住四个平台的按钮位置，而是建立一套平台化思维：

1. 把模型能力、知识、工具和流程拆成可组合的组件。
2. 用可视化工作流快速验证业务假设。
3. 对外部数据、工具权限和副作用操作设置边界。
4. 用测试集、日志和人工审核保证 Agent 的可控性。
5. 为迁移和长期维护保留提示词、数据、接口和评估资产。

{% note primary %}
低代码让“做出第一版”变快，但真正的工程能力体现在：第一版之后能否测量、迭代、审计、迁移，并稳定地服务真实业务。
{% endnote %}
