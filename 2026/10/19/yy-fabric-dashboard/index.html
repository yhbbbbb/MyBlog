从表格到看板：YY 面料数据串联项目复盘

发表于 2026-10-19 分类于 项目笔记 阅读次数：
复盘 YY 面料数据串联看板 Demo：如何整理多来源业务数据、定义可解释的链路指标，并用轻量 Python 服务实现局域网分析与角色权限。

一个看板最先要解决的不是“画什么图”，而是“这个数字到底代表什么”。

项目背景：把分散的数据放进同一条业务链

这个项目是一个面向 YY 面料业务的可运行看板 Demo。数据来自不同阶段的表格和已有链路匹配结果，目标是把 QUO、PPO 与 Bulk 的订单信息放在同一处查看，并支持按客户、面料来源、链路状态、交付日期等条件筛选。

项目代码：yy-fabric-dashboard。文章只讨论代码结构和设计取舍，不包含仓库中的业务数据库或原始数据。

除了总览，项目还包含订单下钻、链路分析、Delivery Date 数据质量检查和用户权限管理。它解决的是“如何把现有数据整理成能查询、能追溯的演示工具”，不是实时生产系统，也不代表所有业务指标都已经具备可靠数据来源。

这里有一条必须坚持的原则：字段缺失就显示待接入或未知，不把缺失值伪装成 0。 如果原始数据没有可靠的 YY、损耗或利用率字段，图表再完整也只会让错误更像事实。

数据如何变成可查询的看板

项目把离线整理与在线查询拆开。scripts/build_demo_db.py 使用 pandas 和 openpyxl 读取 Excel，进行字段规整、日期和数值转换、订单聚合、链路关联及数据质量审计，最后写入 data/dashboard.sqlite。后端查询时将业务库设为只读；登录、角色、页面权限和会话则放在独立的 data/admin.sqlite。

这种拆分让职责比较清楚：构建脚本负责把来源数据变成稳定的查询模型，HTTP 服务负责筛选和返回结果，前端负责呈现与交互。业务库可以只读访问，管理操作不会直接改写分析数据。

几个关键设计取舍

先定统计口径，再做图表

项目分别处理 QUO、PPO、Bulk 的阶段统计，以及 Bulk→PPO、Full chain 的链路统计。单阶段指标不应因为订单没有进入完整链路就被排除；而跨阶段比较则需要严格限定在关联完整、所需字段有效的样本中。两类口径混在一起，会让分母变化而用户无从察觉。

这也是为什么看板需要同时展示链路状态和数据范围。一个数字必须能回答三个问题：统计了哪些记录、排除了哪些记录、使用了什么关联条件。

让异常成为可见的数据

构建脚本会记录无法关联 PPO 的订单、完整链路里缺失或越界的 YY 值等问题，并给出字段和处理建议。与其静默丢弃异常行，不如把异常整理成质量页面：业务人员能看到问题规模，开发人员也能定位原始字段。

数据质量页面并不能自动修复来源数据。它的作用是让错误有迹可循，再由熟悉业务规则的人判断修正方式。

权限要在服务端生效

前端隐藏一个导航项，只能改善界面，不能阻止用户直接请求 API。项目将 API 路由映射到 overview、analytics、orders 等页面权限；服务端验证登录会话和对应权限，无会话返回 401，已登录但未授权返回 403。

角色权限保存在管理库中，用户可绑定多个角色，实际权限由有效角色授权的页面权限组成。密码使用带随机盐的 PBKDF2-HMAC-SHA256 哈希保存，会话令牌通过 HttpOnly Cookie 传递。分析库只读、管理库独立，也减少了账号管理对业务查询数据的影响。

技术栈为何保持轻量

后端使用 Python 标准库的 http.server、sqlite3 和 ThreadingHTTPServer；前端使用原生 HTML、CSS 与 JavaScript，没有引入完整 Web 框架。对局域网演示型工具来说，这让安装和部署路径短，排查问题时也容易沿着请求链定位。

需求 当前实现 这样做的原因与代价
离线整理 Excel pandas、openpyxl 构建 SQLite 适合批量规整；运行构建脚本仍需安装相关 Python 依赖
业务查询 标准库 HTTP 服务、SQLite 部署轻；复杂 API、并发写入和长期运维能力有限
页面交互 原生 HTML/CSS/JavaScript 无前端构建步骤；组件复用和自动化 UI 测试需要自行维护
用户与页面权限 独立 SQLite 管理库、Cookie 会话 适合 Demo 的同源局域网访问；不等同于企业身份认证方案

实践中暴露的边界

第一，数据源路径不能假定每台电脑目录结构相同。当前构建脚本会从项目相邻目录寻找 Excel 文件，这对原始工作目录方便，但换机器或目录后容易选错来源。下一步应把输入路径改为明确配置或命令行参数，并在构建前输出实际读取的文件清单。

第二，构建过程会替换已有的看板数据库。这个行为适合从原始数据重新生成 Demo，但在正式使用前应增加备份、临时文件构建和校验成功后原子替换，避免中途失败留下不可用数据库。

第三，0.0.0.0 监听和普通 HTTP 只适用于受控网络中的演示。项目使用会话 Cookie，但当前没有 HTTPS、完整 CSRF 防护、操作审计和数据范围权限；这些都不能靠“页面上有登录框”来弥补。部署前至少要更换默认管理员口令、限制网络访问、避免把真实业务数据库或原始表格提交到公开仓库，并在需要长期使用时放到 HTTPS 反向代理后。

第四，项目当前没有 YY、损耗、利用率等全部指标的可靠来源，也没有按客户或工厂进行数据范围隔离。界面必须继续标注待接入，不应把占位指标包装成已验证的经营结论。

我从这个项目得到的经验

做数据看板时，最耗时的工作常常不是写查询，而是确认字段定义、去重粒度、匹配规则和缺失值含义。把这些规则沉淀到可重复运行的构建脚本、索引和质量检查中，后续的图表才有可信的基础。

第二个经验是，Demo 可以轻量，但边界必须讲清楚。SQLite 和标准库服务能让原型很快跑起来；只要涉及真实业务数据、多人访问或账号管理，就要重新评估备份、传输加密、并发、审计和权限模型。

接下来最值得做的不是增加更多图表，而是固定数据输入契约、为构建结果增加校验和备份，再用脱敏样本验证统计口径。先让每个数字可解释、每次构建可恢复，再扩大看板的使用范围。
