大数据技术体系（下）：从数据库、数仓到数据中台

发表于 2026-11-04 分类于 技术科普 阅读次数：
继续梳理数据库、数据仓库、数据湖、湖仓和数据中台的边界，解释数据如何从原始记录变成可复用的数据资产和业务能力。

如果上篇回答了“数据放在哪里、如何计算”，这一篇要回答“数据如何被组织、如何可信地共享，以及怎样真正服务业务”。

数据库、数据仓库和数据湖分别解决什么问题？

这几个概念经常被放在一起比较，但它们的出发点有所不同：

系统 核心问题 典型数据 典型使用者
数据库 如何可靠地支撑业务事务 订单、账户、库存 业务系统、应用程序
数据仓库 如何围绕主题分析历史数据 销售、用户、财务指标 分析师、管理者
数据湖 如何低成本保存多种原始数据 日志、文件、事件、半结构化数据 数据工程师、算法工程师
数据中台 如何让组织复用统一的数据能力 指标、标签、主数据、服务 API 多个业务部门和应用

它们不是互相排斥的产品，而是不同层次的系统。一个电商公司可能使用 MySQL 保存订单事务，把订单和日志写入对象存储数据湖，再通过数仓模型生成经营指标，并由数据中台提供统一客户标签给营销系统。

数据库：保证业务交易正确

数据库首先服务在线业务。订单创建、库存扣减和支付状态更新，需要事务、索引、约束和并发控制。关系型数据库强调结构化表、SQL 和 ACID；NoSQL 则针对高并发键值、宽列、文档或图关系做取舍。

这个事务的目标是避免库存扣减成功但订单没有创建，或库存被扣成负数。数据库适合高频、小范围、强一致的读写；如果直接用它承载海量历史日志分析，往往会遇到存储、索引和查询并发压力。

数据仓库：把数据组织成分析模型

数据仓库通常围绕主题域建立稳定的数据模型，并将业务过程转化为事实表和维度表。例如销售分析可以包含：

  • 事实表：订单金额、数量、折扣、支付时间等可度量事实；
  • 维度表：日期、客户、商品、门店、地区等分析维度；
  • 指标口径：成交额是否包含退款，用户是否按注册时间还是下单时间统计。

从 ODS 到 DWD、DWS、ADS

常见分层不是强制标准，但有助于区分职责：

层级 含义 主要工作
ODS 原始数据层 保留源系统同步结果，便于追溯
DWD 明细数据层 清洗、去重、统一字段和粒度
DWS 汇总数据层 按主题域沉淀公共统计结果
ADS 应用数据层 面向报表、接口和具体应用服务

分层的价值在于让数据加工职责可定位：源数据有问题查 ODS，字段清洗有问题查 DWD，公共指标有问题查 DWS，报表展示有问题查 ADS。没有统一粒度和口径时，同一个“销售额”可能在不同报表里得到不同答案。

数据湖：先保存原始数据，再逐步开发价值

数据湖通常以对象存储为底座，保存结构化、半结构化和非结构化数据。它降低了数据进入平台的门槛：日志、JSON、图片、音频、Parquet 和模型特征都可以先保存，再决定如何使用。

但“把文件放进对象存储”不自动成为数据湖。一个可用的数据湖至少需要：

  • 表格式和 Schema 管理；
  • 分区、文件合并和小文件治理；
  • 版本、快照和回滚；
  • 并发写入和数据一致性；
  • 权限、审计和生命周期策略。

Iceberg、Delta Lake 和 Hudi 等表格式就是为了解决对象存储上“表的管理能力”问题。它们通常让分析引擎可以查询一组带版本和元数据的数据文件，而不是直接扫描所有目录。

湖仓：把湖的灵活性和仓的可靠性结合起来

传统数仓擅长结构化分析和稳定性能，数据湖擅长低成本保存多种数据，但两者分开会造成数据复制和口径不一致。湖仓架构尝试在对象存储上使用事务表格式，同时提供数仓需要的 Schema、治理和 SQL 能力。

湖仓不是“所有系统都迁移到一个产品”，而是让存储和计算解耦，让多个引擎共享一份可管理的数据。落地时仍需评估事务能力、引擎兼容性、成本和团队运维能力。

数据中台：从数据集合到组织能力

数据中台经常被误解成一个新数据库，实际上它更像一套组织和技术方法：把分散在各业务线的数据，通过统一标准、公共模型、数据服务和治理机制沉淀为可复用能力。

数据中台解决的典型问题

  1. 重复建设：不同部门各自同步订单、客户和商品，口径却不同；
  2. 数据孤岛：数据存在，但业务系统之间无法发现和调用；
  3. 指标争议：同一个指标在不同报表里有多个计算方式；
  4. 资产难复用：一次清洗结果只能服务一个项目，下次又重新加工；
  5. 治理缺失：不知道数据来自哪里、谁能看、多久更新、能否删除。

中台的核心组成

组成 作用
数据集成 把数据库、日志、消息和文件接入平台
统一模型 统一客户、商品、组织、订单等核心对象
指标平台 维护指标定义、维度、口径和负责人
标签体系 将用户、设备、商品等对象加工成可检索标签
数据服务 通过 API、查询服务或数据产品提供能力
数据治理 质量、血缘、权限、目录、生命周期和审计

中台是否成功，不能只看建设了多少表和接口，而要看业务是否减少重复开发、缩短分析周期、提高数据准确率，并且有人负责持续维护。

图一：从数据源到业务应用的完整链路

这条链路中，数据库承担在线交易，消息和日志承担事件采集，对象存储/数据湖保存原始与明细数据，Spark/Flink 负责批流计算，数仓和数据服务面向最终使用者。治理能力贯穿所有层，而不是只在最后增加一张权限表。

数据治理：让数据可用、可信、可控

数据质量

质量规则可以具体到可执行检查：

质量检查应设置阈值、责任人和失败动作：阻断下游、隔离脏数据、发出告警，还是允许带标记继续运行。只把检查结果写进日志而不通知任何人，不能算真正的质量治理。

元数据与血缘

元数据要回答：这张表是什么、谁负责、多久更新、字段含义是什么、从哪些源表加工而来、被哪些报表和模型使用。血缘可以帮助定位“一个源字段变化会影响哪些下游”。

权限与生命周期

权限设计要遵循最小权限原则，区分表级、行级和列级访问。身份证号、手机号、支付信息等敏感字段应脱敏或禁止进入不必要的开发环境。冷热数据、备份和删除策略也要明确，数据不是保存越久越好。

图二：数据平台的存、算、管、用

“管”这一层用虚线贯穿存储、计算和应用，表示治理不是某个孤立系统，而是每层都要执行的约束。没有治理的数据湖会变成数据沼泽，没有服务层的数据仓库则容易停留在报表项目。

数据如何产生业务价值

数据价值通常经历四步：

  1. 看见事实：报表展示订单、库存、客户和成本；
  2. 解释原因：分析转化率下降、库存积压和客户流失的原因；
  3. 预测趋势：预测销量、风险、需求和设备故障；
  4. 驱动行动：把结果写回营销、供应链、风控和运营系统。

例如“用户近 30 天购买次数”不是最终价值。它需要经过统一用户 ID、去重订单、定义时间窗口、质量校验和服务接口，最终才可能成为营销系统可调用的标签。

选型时不要只看技术名词

可以用几个问题快速缩小方案：

问题 影响的选择
是事务写入还是分析查询？ 数据库或数仓/湖仓
数据是批量到达还是持续事件流？ Spark 或 Flink
是否需要保存原始多媒体和未知结构？ 对象存储/数据湖
查询延迟是毫秒、秒级还是分钟级？ OLTP、服务层、交互式引擎或离线任务
是否需要强一致、回滚和并发写？ 事务数据库或支持事务的表格式
数据是否跨部门复用？ 目录、指标、权限、血缘和数据服务
团队能否维护复杂集群？ 托管云服务优先，减少自建组件

技术体系的目标是解决问题，不是把所有组件都部署一遍。一个小团队可能只需要 PostgreSQL + 对象存储 + 定时 SQL；随着数据规模、实时性和复用需求增加，再引入 Spark、Flink、湖仓表格式和中台能力。

两篇文章的整体结论

大数据技术可以按递进关系理解：

每次技术演进都对应一个新的问题：容量不够，所以需要分布式存储；批处理太慢，所以出现 DAG 和内存计算；业务需要实时响应，所以发展流处理；数据重复和口径混乱，所以需要数仓建模、治理和中台；数据有了却没人使用，所以需要数据服务和业务闭环。

真正成熟的大数据平台不是组件清单，而是一套能让数据可靠流动、被正确解释、受到适当保护，并最终改善业务决策的系统。

综上，我对几个名词的粗浅的归纳为：

数据库： 当下的在线交易

数据湖： 所有的历史数据

大数据： 怎么从数据中挖出/算出价值

数据中台： 怎么把价值变成可复用的服务
